## Section 1 — SQL & Data Warehouse (15 questions)

| # | Question | Answer | Why this answer is good | Project file |
|---|----------|--------|------------------------|--------------|
| 1 | What is a star schema? | A model with fact tables in the center holding measures, surrounded by dimension tables holding descriptive attributes, joined by keys. ShopStar has 3 facts (Sales, Returns, Inventory) and 8 dimensions. | Shows you know the core BI modeling pattern and can name your own schema. | `Documentation/Data_Modeling_Best_Practices.md` |
| 2 | Star schema vs snowflake? | Star keeps dimensions flat (denormalized) for speed and simplicity; snowflake normalizes dimensions into sub-tables to save space but adds joins. I chose star for query speed and easy Power BI relationships. | Shows a design trade-off decision, not just a definition. | `SQL/Warehouse/03_Dimension_Tables.sql` |
| 3 | What is a surrogate key and why use one? | An integer key generated by the warehouse (e.g. `RegionSK`) instead of the business key. It is stable, fast to join, and handles changes/duplicates in source keys. | Demonstrates warehouse best practice and the reason behind it. | `SQL/Warehouse/03_Dimension_Tables.sql` |
| 4 | What is "grain" in a fact table? | The level of detail one row represents. `FactSales` grain is one order line (product × order); getting grain right prevents double-counting. | Grain is a classic senior-level concept many candidates miss. | `Documentation/Technical_Design_Document_Phase3.md` |
| 5 | Explain your ETL layers. | Three layers: Landing (raw CSV as-is), Staging (cleaned and validated), Warehouse (star schema). Each layer has one job, which makes debugging and reloads easy. | Shows structured, production-style ETL thinking. | `SQL/Stored Procedures/06_ETL_Landing_To_Staging.sql` |
| 6 | How did you handle dirty data? | The generator injects NULLs, duplicates, invalid dates, and case mismatches (e.g. "Furniture" vs "FURNITURE"). Staging trims, standardizes case, fixes NULLs to "Unknown/Unbranded", and dedupes. | Shows real data-cleaning experience, not just clean sample data. | `Documentation/Data_Generation_Spec.md` |
| 7 | What is a Kimball -1 member? | An "Unknown" row with surrogate key -1 in each dimension, so fact rows with no matching dimension still join and get counted instead of being dropped. | A specific, advanced technique that impresses interviewers. | `SQL/Warehouse/03_Dimension_Tables.sql` |
| 8 | Why did you use columnstore indexes? | They store data column-by-column and compress heavily, so aggregations over millions of rows read only the needed compressed columns. Ideal for analytics fact tables. | Connects an index choice to a performance reason. | `SQL/Warehouse/05_Indexes_And_ForeignKeys.sql` |
| 9 | Clustered vs non-clustered index? | Clustered defines the physical row order (one per table); non-clustered is a separate lookup structure (many allowed). Facts use clustered columnstore; dimensions use a clustered PK on the surrogate key. | Shows indexing fundamentals applied to your model. | `SQL/Warehouse/05_Indexes_And_ForeignKeys.sql` |
| 10 | How do you enforce referential integrity? | Foreign keys from facts to dimensions, plus the -1 member so orphans still map. This guarantees every fact row joins to a valid dimension. | Shows data-integrity discipline. | `SQL/Warehouse/05_Indexes_And_ForeignKeys.sql` |
| 11 | What is a slowly changing dimension (SCD)? | A dimension whose attributes change over time. Type 1 overwrites; Type 2 keeps history with new rows and date ranges. Surrogate keys make Type 2 possible. | Shows you know how to track history, a common follow-up. | `Documentation/Data_Modeling_Best_Practices.md` |
| 12 | How would you optimize a slow SQL query? | Read the execution plan, look for scans/key-lookups/spills, add or fix indexes, update statistics, and reduce columns/rows early. | Shows a repeatable tuning method, not guessing. | `Documentation/Performance_Optimization_Guide.md` |
| 13 | Views vs stored procedures in your ETL? | Views expose reusable read logic (RFM, ABC, KPI views); stored procedures orchestrate the multi-step ETL loads with control flow and logging. | Shows you use each tool for its right purpose. | `SQL/Views/07_Analytics_Views.sql` |
| 14 | How do you test data quality? | Automated pytest checks for row counts, NULLs, duplicates, and referential gaps after generation, so defects are caught before load. | Shows testing/automation maturity. | `tests/test_data_quality.py` |
| 15 | Why separate development and production data profiles? | Development is 50K orders for fast iteration; production is 500K orders / 2M lines for realistic performance testing. Same generator, different scale. | Shows you plan for scale and testing. | `Python/generate_dataset.py` |

## Section 2 — Power BI & DAX (15 questions)

| # | Question | Answer | Why this answer is good | Project file |
|---|----------|--------|------------------------|--------------|
| 16 | What does `CALCULATE` do? | It evaluates an expression under a modified filter context — the single most important DAX function. Example: `CALCULATE([Total Revenue], FactSales[Channel]="Store")`. | `CALCULATE` is the heart of DAX; a confident answer signals real skill. | `DAX/01_Revenue_And_Sales_Measures.dax` |
| 17 | Row context vs filter context? | Row context is the current row in an iterator (e.g. `SUMX`); filter context is the set of filters from slicers/visuals/`CALCULATE`. `CALCULATE` can turn row context into filter context. | Distinguishing the two contexts is a top DAX discriminator. | `DAX/05_Advanced_Analytics_Measures.dax` |
| 18 | Why use variables (`VAR`) in DAX? | A `VAR` is computed once and reused, improving readability and performance versus repeating a sub-expression. My `Gross Margin %` stores revenue and profit in variables. | Ties a coding habit to performance. | `DAX/02_Profitability_Measures.dax` |
| 19 | `DIVIDE` vs the `/` operator? | `DIVIDE(a,b)` returns blank (or a chosen value) on divide-by-zero instead of an error. Every ratio measure (Margin %, AOV, Return Rate %) uses it. | Shows defensive, production-quality DAX. | `DAX/02_Profitability_Measures.dax` |
| 20 | Give a time-intelligence example. | YoY growth using `SAMEPERIODLASTYEAR` over `DimDate`: compare this period's revenue to the same period last year. Needs a marked, continuous date table. | Time intelligence is expected in almost every BI interview. | `DAX/01_Revenue_And_Sales_Measures.dax` |
| 21 | Measure vs calculated column? | A measure is evaluated at query time in filter context (aggregations like Total Revenue); a calculated column is stored per row at refresh (like `StockStatus`). Prefer measures for aggregations. | Shows you know when to use which — a common mistake area. | `Power BI/ShopStar_Retail.SemanticModel/definition/tables/FactInventory.tmdl` |
| 22 | Why a separate `_Measures` table? | It groups all 98 measures in one place with no data columns, making the model tidy and measures easy to find. | Shows model-organization maturity. | `Power BI/ShopStar_Retail.SemanticModel/definition/tables/_Measures.tmdl` |
| 23 | Single vs bi-directional relationships? | Single (dimension→fact) is the default and safest; bi-directional can cause ambiguity and break RLS, so use it only for specific many-to-many needs. | Shows you understand relationship risks. | `Power BI/ShopStar_Retail.SemanticModel/definition/relationships.tmdl` |
| 24 | Import vs DirectQuery? | Import caches data in memory (fast, used by ShopStar); DirectQuery queries the source live (fresh but slower). I chose Import for dashboard speed. | Ties a mode choice to a reason. | `Documentation/Performance_Optimization_Guide.md` |
| 25 | How did you build "High Margin Products Count"? | `DISTINCTCOUNT` of products whose margin exceeds a threshold. I first set 40%, saw the card go blank, verified max product margin is 39.4%, and set it to 30% → 860 products. | A real debugging story that proves hands-on work. | `DAX/06` / `Documentation/Dashboard_Presentation_Guide.md` |
| 26 | What is TMDL and why use PBIP? | TMDL is the text format for the Power BI model; PBIP saves the report/model as readable text files so changes can be diffed and version-controlled in Git. | Shows modern, source-controlled BI development. | `Power BI/ShopStar_Retail.pbip` |
| 27 | How do slicers stay in sync across pages? | Each Year and Quarter slicer shares a `syncGroup` (SyncYear / SyncQuarter), so selecting on one page applies everywhere. | Shows advanced report interactivity you actually wired. | `Power BI/ShopStar_Retail.Report/definition/report.json` |
| 28 | How would you speed up a slow visual? | Reduce visuals per page, simplify the measure (variables, avoid `FILTER` on big tables), remove high-cardinality fields, and use aggregations. | A structured performance answer. | `Documentation/Performance_Optimization_Guide.md` |
| 29 | What is query folding? | When Power Query pushes its steps back to SQL Server as one query. Foldable steps (filter, remove columns) run on the server; keep them before non-folding steps. | Shows Power Query performance knowledge. | `Power BI/PowerQuery_M_Code_Complete.md` |
| 30 | Why disable auto date/time? | It creates a hidden date table per date column and bloats the model. ShopStar uses one shared `DimDate` instead. | A concrete model-size optimization. | `Documentation/Performance_Optimization_Guide.md` |
